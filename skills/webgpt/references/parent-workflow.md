# 부모가 WebGPT를 실제 협업자로 사용하는 순서

이 문서는 [SKILL.md](../SKILL.md)의 정상 위임 경로를 설명한다. 처음 과제를 설계하거나
활용 방식을 교정할 때 읽는다. 모든 작업에 설치 점검·연결 시험·전체 문서 재독을 추가하는
규칙이 아니다. 등록·전송·수집의 정확한 계약은 각 단계에서 연결한 기존 문서를 따른다.

## 1. 역할과 맡길 결과부터 정한다

**부모 위임 요청**이면 부모가 같은 문제를 다 풀기 전에 WebGPT에 의미 있는 결과를 맡긴다.
초기 저장소 확인은 지침·작업 상태·관련 영역·권한·검증 기준을 정할 정도로 한다. 이미 알려진
결함의 구현을 맡기는 경우는 정당하지만, 독립적인 원인 분석을 요청하고 답까지 강제하거나
부모의 완성본을 다시 쓰게 하는 것을 독립 협업으로 계산하지 않는다.

**현재 작업 토큰을 받은 웹 작업자**라면 선택된 connector의 `get_task`로 배정을 읽고 수행한다.
부모용 등록 CLI를 다시 찾거나 다른 웹 작업자를 생성하지 않는다. 이전 채팅의 토큰은 재사용하지
않는다. **WebGPT 저장소 자체의 유지보수 요청**은 별도다. 사용자가 직접 수정·PR을 요청했다면
그 권한과 도구로 작업하며, WebGPT라는 이름이 등장했다는 이유만으로 재귀 위임하지 않는다.

| 맡길 일 | 웹 ChatGPT가 담당할 결과 | 부모가 남겨 둘 역할 |
| --- | --- | --- |
| 원인 분석·설계 검토 | 관련 구현/자료 조사, 대안 비교, 근거와 불확실성을 포함한 판단 | 범위 결정, 중요한 근거 대조, 최종 선택 |
| 저장소 읽기 전용 리뷰 | 등록 프로젝트를 직접 읽은 결함/위험 평가. 결함이 없으면 없다고 보고 | 재현·반례·심각도 확인. 수정은 별도 권한일 때만 |
| 범위가 정해진 구현 | 실제 프로젝트 텍스트 변경, 필요한 테스트 코드와 변경 근거 | 변경 검토, 실제 로컬 실행·통합·승인된 Git/PR |
| 자료 조사·비교·보고서 | 허용되고 실제 제공되는 조사 도구와 입력을 이용한 분석/산출물 | 출처·핵심 주장 확인과 수용 판단 |

일곱 MCP 도구는 로컬 프로젝트와 결과를 연결하는 통로이지 웹 모델의 분석 능력 범위가 아니다.
과업상 필요한 웹 조사나 첨부 해석도 실제 채팅의 지원 도구와 사용자 권한 안에서 활용한다.
반대로 도구가 있을 것이라고 가정하거나 추가 외부 연결·파일 전송 권한을 임의로 부여하지 않는다.
이 포크의 MCP에는 셸·Git이 없다. 그것만으로 파일 읽기·수정·분석 전체가 불가능한 것은 아니다.
실행하지 못한 검사는 작업자가 `NOT_RUN`으로 남기고 부모가 허용된 환경에서 맡는다.

## 2. 작업 브리프는 짧게, 결정 여지는 남긴다

등록 `instructions`에 목표, 필요한 맥락, 산출물/수용 기준, 소유 범위와 중요한 금지사항을
담는다. 일반 과제에 MCP 호출 목록을 복사하거나 모든 조사·편집 순서를 지시하지 않는다.
사용자가 요청한 형식과 깊이를 보존하고, WebGPT가 범위 안에서 도구·구현·검사를 선택하게 한다.

다음은 **설명용 브리프**다. 실제 증상과 범위로 바꾸며, 정답을 미리 정한 연결 시험이 아니다.

```text
로그인 만료 뒤 재시도 동작이 일관되지 않은 원인을 검토하고 필요한 최소 수정을 해 주세요.
등록된 프로젝트의 관련 구현과 테스트를 직접 조사해 원인과 대안을 판단해 주세요.
담당 범위는 인증/재시도 로직과 직접 관련된 테스트입니다. 다른 작업자의 변경은 보존하세요.
무조건 재시도나 권한 완화로 회피하지 말고, 결함이 확인되지 않으면 억지로 수정하지 마세요.
결과에 판단 근거, 실제 변경, 회귀 검사 의도와 미실행 검증을 포함해 주세요.
로컬 테스트·빌드·Git 통합은 부모가 담당합니다.
```

독립성이 가치 있는 검토라면 부모의 가설은 가설로 전달한다. 필수 계약과 검증 기준은 명확히
하되 결론을 맞추게 하지 않는다. 길고 일관된 과제는 한 채팅에 맡긴다. 병렬화는 독립된 결과와
서로 겹치지 않는 쓰기 범위가 있을 때만 사용한다. 이 담당 범위는 협업 규칙이며 파일별 보안
허용 목록을 새로 만드는 것은 아니다. 의존하는 구현과 테스트는 순서대로 진행할 수 있다.

## 3. 입력 전달과 실제 실행 환경을 맞춘다

기존의 정상 연결을 재사용한다. 부모가 사용하는 설치 스킬 경로·명시적 `WEBGPT_CONFIG`와
브라우저 도구/프로필을 식별하고, 변경이나 오류가 있을 때 [setup.md](setup.md)로 확인한다.
`dispatch preflight`는 일반 Node에서 실행한다. CUA 내부로 Node helper를 가져오지 않는다.
설정 이름, `/health`, GitHub의 머지 상태만으로 해당 브라우저/프로젝트가 준비됐다고 보지 않는다.

| 입력 | 사용하는 경로 | 피할 우회 |
| --- | --- | --- |
| 로컬 프로젝트 텍스트 | 정확한 프로젝트 루트의 read/edit grant | 부모가 매번 파일을 복사하거나 저장소 ZIP 첨부로 직접 접근을 대체 |
| 명시적으로 제공할 텍스트 자료 | 등록의 `inputs`, 작업자의 `read_input` | 긴 자료를 프롬프트마다 중복 삽입, 부분 읽기를 원문 전체로 취급 |
| 실제 첨부가 필요한 PDF·이미지 등 | 지원되는 브라우저 업로드와 [file-uploads.md](file-uploads.md) | MCP 텍스트 읽기가 첨부를 만들었다고 주장, 원격 sandbox 경로를 Windows 로컬 경로로 취급 |

등록은 [workspace.md의 Per task](workspace.md#per-task)를 따른다. 기본 형태는 그대로다.

```json
{
  "id": "new-owned-task-id",
  "instructions": "여기에 이번 작업의 브리프를 작성합니다.",
  "inputs": {},
  "workspace": {"root": "/absolute/project", "mode": "edit"}
}
```

```text
node <skill>/scripts/client.mjs dispatch preflight
node <skill>/scripts/client.mjs register <private-task.json>
```

리뷰는 `read`, 파일이 필요 없는 조사는 `workspace`를 생략한다. 프로젝트와 비공개 runtime은
분리하고, 불필요한 비밀이 있으면 권한에 맞는 정리된 사본을 사용한다. 등록 응답의 작업 토큰은
정확한 작업 채팅에만 비공개로 전달한다. controller key는 전달하지 않는다. 이미 전달했을 수
있는 작업에는 이 예시의 새 ID를 적용하지 않고 먼저 기존 작업을 대조한다.

## 4. 기존 전송·대기·수집을 한 흐름으로 사용한다

[dispatch.md](dispatch.md)의 split CLI를 사용해 한 작업의 비공개 전송 원장과 실제 관찰을
연결한다. 모드/connector/소유 대상/본문을 확인하고, `begin` 성공 뒤 한 번의 지원된 입력·전송을
수행한다. 필요한 첨부는 최초 `requiredAttachments` 선언과 **업로드 전 begin**, 준비 완료 확인,
같은 새 사용자 메시지의 첨부 이름·개수 확인을 모두 지킨다. 누락이나 불확실성이 있으면 원래
시도를 보존한다. 세부 관찰 형식을 추측하거나 기대값을 실제 브라우저 증거로 복사하지 않는다.

등록된 실제 과제의 `get_task`와 첫 필요한 파일 읽기가 성공하면 그 과제의 접근 근거가 된다.
매번 별도 임시 파일 생성·삭제를 시켜야 하는 것은 아니다. 필요한 직접 접근이 없으면 그 부분을
차단 상태로 보고하며, 프로젝트 구현을 부모가 대신 패치 적용하는 방식으로 조용히 바꾸지 않는다.
별개의 허용된 분석은 계속할 수 있지만, 입력이 없는 코드 수정이나 검증을 수행했다고 보고하지 않는다.

작업 중에는 부모가 비충돌 통합 준비나 다른 독립 작업을 할 수 있다. 같은 문제를 다시 풀거나
같은 파일을 동시에 바꾸지 않는다. 기다려야 한다면 다음 기존 경로를 사용한다.

```text
node <skill>/scripts/client.mjs wait <owned-task-id>
```

비어 있는 HTTP 갱신은 클라이언트 내부에 남긴다. 이벤트/복구 신호/15분 백업 확인 시점에만
해당 미완료 채팅을 확인하고, 계속 진행 중이라는 이유로 재전송하지 않는다. 부모 실행이 끝난
뒤 자동으로 깨어나는 기능은 없다. 결과가 나오면 브라우저 답변·저장 결과·관련 변경을 보존하고
핵심 근거와 실제 로컬 검사를 확인한다. UI의 완료 설명이나 해시 일치가 내용의 정답은 아니다.

수용/부분수용/거부와 미검증 항목을 기록한 뒤 [수집 계약](workspace.md#completion-and-lifecycle)의
`collect <task-id>`를 사용한다. 정상 CLI가 이미 수행하는 사후 확인을 수동 HTTP 호출이나 전체
`reconcile`로 매번 중복하지 않는다. 복구·응답 유실이면 기존 명시적 재개 절차를 사용한다.
보고서 제출·수집과 최종 채팅 답변 완료는 별도로 확인한다. 저장 결과는 검토 후 곧바로 수집해
토큰을 회수하되, 답변이 아직 작성 중이면 생성을 중지하지 않고 완료까지 기다린다. 최종 답변의
실제 내용과 생성 종료를 관측하고 저장 결과와 중요한 주장이 일치하는지 확인한 뒤 소유 탭을
닫는다. 명시적 취소나 안전상 중단은 완료된 답변과 구분해 기록한다. 채팅은 보존한다. 정확한 조건은
[chat-lifecycle.md](chat-lifecycle.md), 수집 오류 상세는 [collection-details.md](collection-details.md)에 있다.

## 5. 실제 실패 근거를 같은 채팅으로 되돌린다

| 확인한 상태 | 부모의 다음 행동 |
| --- | --- |
| 작업 진행 중, 정상 | 원래 작업을 계속 기다린다. 대체 등록/동일 브리프 재전송을 하지 않는다. |
| 전송·파일 변경·결과 상태 불확실 | 원래 ID·원장·채팅·결과를 대조하고 필요한 복구만 수행한다. 새 작업으로 우회하지 않는다. |
| 종료·수집 및 최종 답변 완료 확인, 실제 후속 작업 필요 | 같은 채팅에 새 ID/토큰과 새 작업 원장을 연결한다. 이전 기록은 보존한다. 명시적으로 중단된 답변은 그 상태를 별도로 기록한다. |
| 검사 불가 또는 같은 실패 반복 | 실제 한계와 부분 결과를 남긴다. 실패를 없애려 검사를 완화하거나 작업을 복제하지 않는다. |

후속 브리프에는 실제 실패한 검사, 관련 출력, 기대한 동작과 수정 범위를 전달한다. 단순히
“처음부터 다시 검토”라고 하지 않는다. 기존 작업이 종료됐으면 파일 접근을 되살리지 않고
새 권한을 등록한다. 이전 결과가 아직 수집되지 않았다면 먼저 검토·수집/명시적 종료 판단을
마친다. 채팅을 유지하는 것과 task ID/토큰을 재사용하는 것은 다르다.

## 6. 최종 보고에는 실제 기여가 보여야 한다

사용자가 요구한 결과를 먼저 제시하고, 필요한 경우 아래 구분을 짧게 덧붙인다. 이는 새
`submit_result` JSON 스키마나 완료 저장소가 아니라 부모 보고/기존 원장에 남길 내용이다.

```text
WebGPT 기여: 실제 수행한 분석·변경과 그 근거. 없으면 미실행 또는 차단 이유.
부모 처리: 확인한 근거, 실행한 검사, 통합·PR 등 실제 수행한 부분.
결과 판단: 수용 / 부분수용 / 거부, PASS / FAIL / NOT_RUN과 남은 조건.
```

유용한 무결함 리뷰나 대안 기각도 성과다. 편집 파일 수, 일곱 도구의 전부 사용, CI 통과 수를
활용률로 삼지 않는다. 부모가 전체를 직접 수행한 작업이나 연결 probe는 구분해서 보고한다.
운영 적용과 실제 효과의 확인은 요청된 경우 [parent-acceptance.md](parent-acceptance.md)를 따른다.
