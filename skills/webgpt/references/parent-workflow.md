# 부모가 WebGPT를 실제 협업자로 사용하는 순서

이 문서는 [SKILL.md](../SKILL.md)의 정상 위임 경로를 설명한다. 처음 과제를 설계하거나
활용 방식을 교정할 때 읽는다. 모든 작업에 설치 점검·연결 시험·전체 문서 재독을 추가하는
규칙이 아니다. 목표는 **부모 모델의 작업·개입·맥락 비용을 줄이고, 실제 권한과 수용 한도
안에서 웹 워커가 완결할 수 있는 일을 최대한 맡는 것**이다. 사용량 소진이나 무조건 병렬화가
목표는 아니다. Git에 올라간 작업만이 아니라 일반 로컬 폴더·제공된 텍스트·첨부·자료 분석·
문서/미디어 생성·연결된 앱 작업에도 동일하게 적용한다. 입력과 산출물별 완료 기준은
[일반 작업 완료 지침](task-completion.md)에 있다. 등록·전송·수집의 계약은 기존 문서를 따른다.

## 1. 역할과 맡길 결과부터 정한다

**부모 위임 요청**이면 부모가 같은 문제를 다 풀기 전에 WebGPT에 의미 있는 결과를 맡긴다.
초기 확인은 실제 입력·기존 작업 상태·출력 위치·권한·검증 기준을 정할 정도로 한다. 이미 알려진
결함의 구현을 맡기는 경우는 정당하지만, 독립적인 원인 분석을 요청하고 답까지 강제하거나
부모의 완성본을 다시 쓰게 하는 것을 독립 협업으로 계산하지 않는다.

**현재 작업 토큰을 받은 웹 작업자**라면 선택된 connector의 `get_task`로 배정을 읽고 수행한다.
부모용 등록 CLI를 다시 찾거나 다른 웹 작업자를 생성하지 않는다. 이전 채팅의 토큰은 재사용하지
않는다. **WebGPT 저장소 자체의 유지보수 요청**은 별도다. 사용자가 직접 수정·PR을 요청했다면
그 권한과 도구로 작업하며, WebGPT라는 이름이 등장했다는 이유만으로 재귀 위임하지 않는다.

| 맡길 일 | 웹 ChatGPT가 담당할 결과 | 부모가 남겨 둘 역할 |
| --- | --- | --- |
| 원인 분석·설계 검토 | 관련 구현/자료 조사, 대안 비교, 근거와 불확실성을 포함한 판단 | 범위 결정, 중요한 근거 대조, 최종 선택 |
| 저장소 읽기 전용 리뷰 | 직접 조사와 가능한 재현·반례 검토, 근거/심각도 판단. 무결함도 유효한 결과 | 핵심 근거와 위험 중심 수용 판단. 수정·게시 권한은 별도 |
| 범위가 정해진 구현 | 실제 변경, 테스트 작성과 가능한 실행·실패 분석·교정까지 | 근거 대조, 워커가 못 하는 환경 전용 검사·필요한 로컬 통합만 |
| 승인된 PR 결과 | 실제 GitHub 도구로 게시, 최종 head의 CI·리뷰 확인과 필요한 수정까지 | 최종 PR·리비전·검증 근거와 남은 위험 확인. 같은 작업 재수행 금지 |
| 자료 조사·비교·보고서 | 필요한 조사·분석·사실/원문 대조와 요청된 보고서 완성 | 핵심 근거와 수용 판단 |
| 데이터·문서·미디어 산출물 | 실제 입력 처리, 요청 형식 생성, 계산/내용/레이아웃 검증과 교정·전달 | 부족한 근거 또는 워커가 못 하는 최종 저장/전달만 |
| 연결된 앱의 승인된 수정 | 정확한 원본 읽기, 요청 범위 변경과 가능한 결과 재조회 | 실제 권한/확인 장벽과 미충족 기준만 |

일곱 MCP 도구는 로컬 프로젝트와 결과를 연결하는 통로이지 웹 모델의 분석 능력 범위가 아니다.
과업상 필요한 웹 조사나 첨부 해석도 실제 채팅의 지원 도구와 사용자 권한 안에서 활용한다.
반대로 도구가 있을 것이라고 가정하거나 추가 외부 연결·파일 전송 권한을 임의로 부여하지 않는다.
이 포크의 MCP에는 셸·Git이 없다. 그것만으로 파일 읽기·수정·분석 전체가 불가능한 것은 아니다.
별도 GitHub 앱의 쓰기·PR·CI·리뷰 도구는 현재 세션에서 탐색한다. 셸이나 `gh`가 없다는 이유로
원격 게시도 불가능하다고 판단하지 않는다. 게시가 승인된 과제는 별도 제한이 없는 한 최종
CI·리뷰 후속 처리까지 워커에게 맡긴다. 게시 승인이 없는 리뷰/로컬 수정은 PR을 만들지 않는다.
사용자가 Pro 직접 게시를 지정했다면 부모 게시로 조용히 바꾸지 않는다. [GitHub 작업 안내](github-workflow.md)에 따라 실제 도구와 실패 단계를
구분하고, 실행하지 못한 로컬 검사는 `NOT_RUN`, 실제 CI 실행은 해당 커밋의 결과로 기록한다.

## 2. 작업 브리프는 짧게, 결정 여지는 남긴다

수동 전달·배정서 개정·선행 명세 인수·부모 전용 검사 때문에 인계 비용이 커지면
[개정별 인계와 검증 피드백](worker-handoff.md)을 사용한다. 실제 환경과 가능한 도구를
먼저 구분하고, `client.mjs handoff`로 선택한 입력의 해시·누락 영향과 검사 당시 해시를
묶을 수 있다. 이 명령은 파일 전달·명령 실행·자동 배정·인수를 수행하지 않는다.
모델 배정은 작업 계약과 분리하며, 역할 분리는 단독 작업보다 실익이 있을 때만 한다.

등록 `instructions`에 목표, 실제 입력과 접근 경로, 출력 형식/위치, 수용 기준, 담당 범위와
중요한 제한을 담는다. 부모가 읽은 로컬 스킬 문서를 워커도 읽었다고 가정하지 말고 필요한
완료 범위를 실제 배정에 넣는다. 워커에게 접근 불가능한 지침 경로만 보내지 않는다. 일반 과제에 MCP 호출 목록을 복사하거나
모든 조사·편집 순서를 지시하지 않는다.
사용자가 요청한 형식과 깊이를 보존하고, WebGPT가 범위 안에서 도구·구현·검사를 선택하게 한다.

다음은 **설명용 공통 브리프**다. 대괄호를 실제 과제에 맞게 바꾸며 연결 시험으로 대체하지 않는다.

```text
[실제 입력과 접근 경로]를 사용해 [목표]를 [형식과 전달 위치]로 완성해 주세요.
현재 제공되는 도구와 승인 범위에서 필요한 조사·가공·생성/수정·검증·교정까지 수행해 주세요.
제가 이어서 실행할 방법이나 초안으로 끝내지 말고 요청된 산출물과 확인한 근거를 전달해 주세요.
Git이나 CI는 해당 과제에 필요한 경우에만 사용하세요. [보존 사항과 명시적 제한]을 지켜 주세요.
한 단계가 막히면 독립적으로 가능한 작업을 마치고 정확한 한계와 최소한의 남은 조치를 알려 주세요.
요청하지 않은 외부 발송·공유·권한 변경은 하지 말고 필수 확인 절차를 유지해 주세요.
```

PR까지 요청된 과제는 브리프에 정확한 저장소·기준 ref·게시 범위와 CI/리뷰 완료 기준을 넣는다.
워커가 관련 도구를 직접 확인하고 수정→검증→교정→게시·리뷰까지 수행하며, 부모는 초안이나
첫 커밋을 최종 결과로 받지 않는다. 도구·권한·환경상 실제 막힌 단계만 이유와 함께 넘긴다.
추가 권한, 유료 사용, 머지·배포·서비스 재시작은 이 기본 배정으로 승인되지 않는다.

독립성이 가치 있는 검토라면 부모의 가설은 가설로 전달한다. 필수 계약과 검증 기준은 명확히
하되 결론을 맞추게 하지 않는다. 길고 일관된 과제는 한 채팅에 맡긴다. 병렬화는 독립된 결과와
서로 겹치지 않는 쓰기 범위가 있을 때만 사용한다. 이 담당 범위는 협업 규칙이며 파일별 보안
허용 목록을 새로 만드는 것은 아니다. 의존하는 구현과 테스트는 순서대로 진행할 수 있다.

## 3. 입력 전달과 실제 실행 환경을 맞춘다

기존의 정상 연결을 재사용한다. 부모가 사용하는 설치 스킬 경로·명시적 `WEBGPT_CONFIG`와
브라우저 도구/프로필을 식별하고, 변경이나 오류가 있을 때 [setup.md](setup.md)로 확인한다.
`dispatch preflight`는 일반 Node에서 실행한다. 같은 부모 세션·호스트·설치 리비전·설정이
유지되면 그 결과와 검증한 연결 식별 정보를 재사용하며, 매 작업마다 전체 도구 탐색이나
설치 검증을 반복하지 않는다. 재시작, 설정·엔드포인트·스키마·계정·프로필 변경 또는 오류가
있으면 영향을 받는 준비 상태를 다시 확인한다. 작업별 grant와 전송 시 실제 모드·connector·
대상·본문 확인은 생략하지 않는다. 별도 캐시나 완료 권한을 만들지 않고 기존 비공개 설정
기록과 부모 세션의 근거를 사용한다. CUA 내부로 Node helper를 가져오지 않는다.
설정 이름, `/health`, GitHub의 머지 상태만으로 해당 브라우저/프로젝트가 준비됐다고 보지 않는다.

| 입력 | 사용하는 경로 | 피할 우회 |
| --- | --- | --- |
| 일반 로컬 폴더·미커밋 변경 | 정확한 폴더 루트의 read/edit grant. Git 불필요 | 원격 HEAD로 로컬 입력을 대체하거나 부모가 파일을 매번 중계 |
| 원격 저장소/PR만으로 완결되는 과제 | GitHub의 기준 SHA와 작업 브랜치. 불필요한 workspace 생략 | 부모에게 clone·패치 적용·로컬 동기화를 새로 요구 |
| 명시적으로 제공할 텍스트 자료 | 등록의 `inputs`, 작업자의 `read_input` | 긴 자료를 프롬프트마다 중복 삽입, 부분 읽기를 원문 전체로 취급 |
| 첨부 데이터·PDF·이미지 등 | 실제 첨부와 지원 분석/생성 도구. 업로드는 [file-uploads.md](file-uploads.md) | 이미 접근 가능한 입력을 부모가 다시 가공, 필요한 원본을 요약으로 대체 |
| 연결된 문서·표·레코드 | 해당 앱의 실제 읽기/수정 도구와 원본 ID·버전/재조회 근거 | 로컬 사본이나 Git 등록을 필수 단계로 추가 |

입력별 기준 원본과 결과별 전달 위치를 정한다. 여러 자료를 함께 쓰더라도 하나의 Git 저장소로
모을 필요는 없다. 로컬·첨부·앱의 실제 버전을 사용하고, 지원할 때만 해시/버전을 근거로 남긴다.
두 위치 모두 수정해야 한다면 그 이유와 통합 담당을 명시한다. 워커 sandbox의 파일 생성은
부모 디스크 저장이 아니며 원격 PR도 로컬 HEAD/index를 갱신하지 않는다.
등록은 [workspace.md의 Per task](workspace.md#per-task)를 따른다. 로컬 수정의 예시는 다음과 같다.

```json
{
  "id": "new-owned-task-id",
  "instructions": "여기에 이번 작업의 브리프를 작성합니다.",
  "inputs": {},
  "workspace": {"root": "/absolute/project", "mode": "edit"}
}
```

아래 preflight는 위 조건에서 재사용할 수 있지만, 새로운 작업의 등록은 별도로 수행한다.

```text
node <skill>/scripts/client.mjs dispatch preflight
node <skill>/scripts/client.mjs register <private-task.json>
```

로컬 폴더 리뷰는 `read`, 로컬 접근이 필요 없는 텍스트·첨부·앱 작업은 `workspace`를 생략한다.
프로젝트와 비공개 runtime은
분리하고, 불필요한 비밀이 있으면 권한에 맞는 정리된 사본을 사용한다. 등록 응답의 작업 토큰은
정확한 작업 채팅에만 비공개로 전달한다. controller key는 전달하지 않는다. 이미 전달했을 수
있는 작업에는 이 예시의 새 ID를 적용하지 않고 먼저 기존 작업을 대조한다.

## 4. 기존 전송·대기·수집을 한 흐름으로 사용한다

[dispatch.md](dispatch.md)의 split CLI를 사용해 한 작업의 비공개 전송 원장과 실제 관찰을
연결한다. 모드/connector/소유 대상/본문을 확인하고, `begin` 성공 뒤 한 번의 지원된 입력·전송을
수행한다. 필요한 첨부는 최초 `requiredAttachments` 선언과 **업로드 전 begin**, 준비 완료 확인,
같은 새 사용자 메시지의 첨부 이름·개수 확인을 모두 지킨다. 누락이나 불확실성이 있으면 원래
시도를 보존한다. 세부 관찰 형식을 추측하거나 기대값을 실제 브라우저 증거로 복사하지 않는다.

등록된 실제 과제의 `get_task`와 첫 필요한 파일 읽기가 성공하면 그 과제의 접근 근거가 된다.
매번 별도 임시 파일 생성·삭제를 시켜야 하는 것은 아니다. 필요한 직접 접근이 없으면 그 부분을
차단 상태로 보고하며, 프로젝트 구현을 부모가 대신 패치 적용하는 방식으로 조용히 바꾸지 않는다.
별개의 허용된 분석은 계속할 수 있지만, 입력이 없는 코드 수정이나 검증을 수행했다고 보고하지 않는다.

작업 중에는 부모가 비충돌 통합 준비나 다른 독립 작업을 할 수 있다. 같은 문제를 다시 풀거나
같은 파일을 동시에 바꾸지 않는다. 한 작업의 결과를 기다리고 검토할 때는 다음을 사용한다.

```text
node <skill>/scripts/client.mjs review <owned-task-id>
```

기본 `review`는 기존 작업별 대기와 SHA 검증·전체 본문 읽기를 한 호출로 묶는 **읽기 전용**
부모 명령이다. 반환된 `review.content`는 검증한 동일 바이트를 해석한 텍스트이며,
내용을 표시하려고 파일을 다시 열 필요가 없다. 수용·수집·토큰 회수는 하지 않는다.
`review: null`이면 복구/중단/백업 확인/이벤트 없는 종료 상태를 살펴야 하며 성공으로
취급하지 않는다. 여러 작업의 메타데이터만 기다릴 때는 기존 `wait <id> ...`를 유지한다.
전체 반환 계약·비공개 출력·크기 제한은 [result-review.md](result-review.md)에 있다.

긴 결과는 `review <owned-task-id> --save-result <new-absolute-private-directory>`로
검증한 전문과 헤더 포함 20,000자(UTF-16 단위) 이하의 번호별 메시지 파일을 함께 저장한다.
이 명시적 옵션은 로컬 파일을 쓰며 `review.content` 대신 `review.saved`를 반환한다.
저장 위치의 전문 또는 필요한 모든 조각을 읽고 인수한다. 원본·조각의 SHA와 순서·범위는
manifest에 남으며, 기존 디렉터리는 덮어쓰지 않는다. Windows–WSL 간에는 실제 결과를
소유한 환경의 Node·설정으로 저장하고 소비 환경에서 바이트를 확인한다.
저장 후에는 `read-export <absolute-directory> --task-id <owned-task-id>
--expected-sha256 <기존-review의-SHA>`로 controller 없이 다시 검증·조회한다.
매번 전체 패키지를 검증하고 JSON 이스케이프·메타데이터·줄바꿈까지 20,000자 이내로 반환한다.
`--offset <nextOffset>`을 이어 읽되, 이 값은 0부터 시작하는 UTF-16 위치이며 `review`의 행 번호와 다르다.
원래 review의 ID·SHA를 유지하고 마지막 `nextOffset: null`만으로 앞부분도 읽었다고 판단하지 않는다.
이 검증은 저장본의 바이트·구조 검사이며 현재 작업 상태나 최종 채팅 답변을 확인한 것은 아니다.
채팅 조회의 `truncated`는 전문 미확보다. `hasMore: false`만으로 전체 열람으로 처리하거나
같은 제한 조회를 반복하지 않는다. 저장된 제출 보고서와 최종 채팅 답변을 구분하며,
로컬 메시지 파일 생성이 실제 ChatGPT의 여러 메시지 게시를 의미하지는 않는다.
검토 후에는 [review-evidence.md](review-evidence.md)의 `dispatch record-review`로
보고서 검토 범위·판정, 채팅 생성 상태·본문 잘림, 상호 대조와 차이 처리 상태를 따로 기록할 수 있다.
전송이 확인된 기존 작업 기록만 갱신하며, 수동 작업은 생성 API와 기존 부모 기록을 사용한다.
`reportedReviewComplete`는 검토 완료 보고이지 작업 성공·결과 승인·수집·탭 닫기 허가가 아니다.
일부만 읽은 답변이나 처리하지 않은 차이는 그대로 미완료로 남긴다.

비어 있는 HTTP 갱신은 클라이언트 내부에 남긴다. 이벤트/복구 신호/15분 백업 확인 시점에만
해당 미완료 채팅을 확인하고, 계속 진행 중이라는 이유로 재전송하지 않는다. 부모 실행이 끝난
뒤 자동으로 깨어나는 기능은 없다. 결과가 나오면 반환 본문·브라우저 답변·관련 변경을 보존하고
관련 변경·핵심 주장·생성 산출물·검사 근거의 입력/결과 버전과 환경을 대조한다. 충분한 워커 근거를
재사용하고 같은 분석·전체 테스트를 부모가 관행적으로 반복하지 않는다. 중요한 위험, 부족한 근거,
후속 파일 변경 또는 환경 차이가 있을 때 필요한 검사만 추가한다. 미충족 필수 수용 기준은
미해결로 남긴다. UI의 완료 설명이나 해시 일치가 내용의 정답은 아니다.
관측한 본문은 이후 파일이 바뀌어도 최신이라는 뜻이 아니며, 수집은 기존 검사를 새로 수행한다.

수용/부분수용/거부와 미검증 항목을 기록한 뒤 [수집 계약](workspace.md#completion-and-lifecycle)의
`collect <task-id>`를 사용한다. 정상 CLI가 이미 수행하는 사후 확인을 수동 HTTP 호출이나 전체
`reconcile`로 매번 중복하지 않는다. 복구·응답 유실이면 기존 명시적 재개 절차를 사용한다.
보고서 제출·수집과 최종 채팅 답변 완료는 별도로 확인한다. 저장 결과는 검토 후 곧바로 수집해
토큰을 회수하되, 답변이 아직 작성 중이면 생성을 중지하지 않고 완료까지 기다린다. 최종 답변의
실제 내용과 생성 종료를 관측하고 저장 결과와 중요한 주장이 일치하는지 확인한 뒤 소유 탭을
닫는다. 명시적 취소나 안전상 중단은 완료된 답변과 구분해 기록한다. 채팅은 보존한다. 정확한 조건은
[chat-lifecycle.md](chat-lifecycle.md), 수집 오류 상세는 [collection-details.md](collection-details.md)에 있다.

## 5. 실제 실패 근거를 같은 채팅으로 되돌린다

| 확인한 상태 | 부모의 다음 행동 |
| --- | --- |
| 작업 진행 중, 정상 | 원래 작업을 계속 기다린다. 대체 등록/동일 브리프 재전송을 하지 않는다. |
| 전송·파일 변경·결과 상태 불확실 | 원래 ID·원장·채팅·결과를 대조하고 필요한 복구만 수행한다. 새 작업으로 우회하지 않는다. |
| 종료·수집 및 최종 답변 완료 확인, 실제 후속 작업 필요 | 같은 채팅에 새 ID/토큰과 새 작업 원장을 연결한다. 이전 기록은 보존한다. 명시적으로 중단된 답변은 그 상태를 별도로 기록한다. |
| 검사 불가 또는 같은 실패 반복 | 실제 한계와 부분 결과를 남긴다. 실패를 없애려 검사를 완화하거나 작업을 복제하지 않는다. |

후속 브리프에는 실제 실패한 검사, 관련 출력, 기대한 동작과 수정 범위를 전달한다. 단순히
“처음부터 다시 검토”라고 하지 않는다. 기존 작업이 종료됐으면 파일 접근을 되살리지 않고
새 권한을 등록한다. 이전 결과가 아직 수집되지 않았다면 먼저 검토·수집/명시적 종료 판단을
마친다. 채팅을 유지하는 것과 task ID/토큰을 재사용하는 것은 다르다.

## 6. 최종 보고에는 실제 기여가 보여야 한다

워커는 요청된 산출물에 짧은 수용 요약을 붙인다: 결과, 변경/리비전, 실제 검사 근거,
한계, 남은 부모 조치(없으면 없음). Git이 없으면 실제 입력/출력 식별 정보로 대신하고 없는
버전·해시를 만들지 않는다. 파일은 접근 가능한 첨부/다운로드·앱 참조로 전달하고, 생성·검증·
요청 위치 저장을 구분한다. 텍스트 결과 수집은 바이너리 파일 전송이 아니다.
상세 로그·전체 조사 기록은 승인되고 접근 가능한 위치에 남기고 부모에게 매번 원문을 중계하지 않는다. 요청된 보고서의 깊이·분량을 임의로 줄이거나
부모가 못 읽는 sandbox 경로만 근거로 넘기지 않는다. 이는 새 `submit_result` 스키마가 아니다.
부모는 다음을 기존 원장과 최종 보고에 짧게 구분한다.

```text
WebGPT 기여: 실제 수행한 분석·변경과 그 근거. 없으면 미실행 또는 차단 이유.
부모 처리: 확인한 근거, 실행한 검사, 통합·PR 등 실제 수행한 부분.
결과 판단: 수용 / 부분수용 / 거부, PASS / FAIL / NOT_RUN과 남은 조건.
```

유용한 무결함 리뷰나 대안 기각도 성과다. 편집 파일 수, 일곱 도구의 전부 사용, CI 통과 수를
활용률로 삼지 않는다. 부모가 전체를 직접 수행한 작업이나 연결 probe는 구분해서 보고한다.
실제 과제에서 부모의 능동 개입 횟수·추가 검사/재구현과 그 이유, 워커 내부 교정,
최종 수용 결과를 함께 본다. 필수 검사를 생략해 줄인 개입은 개선으로 계산하지 않는다.
토큰·비용·시간 절감은 측정하지 않았다면 미측정으로 남기며 별도 원장/진단 루프를 만들지 않는다.
운영 적용과 실제 효과의 확인은 요청된 경우 [parent-acceptance.md](parent-acceptance.md)를 따른다.
