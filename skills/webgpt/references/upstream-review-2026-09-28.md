# WebGPT 포크와 업스트림 main 비교 — 2026-09-28

이 문서는 특정 커밋의 소스·도구 계약·운영 지침을 비교한 설계 검토입니다.
동일 과제의 속도·사용량·성공률을 측정한 벤치마크나 현재 사용자 설치의 검증 결과가
아닙니다. 이후 main이 바뀌어도 아래의 기준 커밋은 그대로 유지합니다.

## 1. 결론

**프로젝트 파일 권한, 수정 충돌 거부, 복구 증거와 채팅 보존을 기본값으로 유지하려면
22nsuk 포크가 적합합니다. 웹 ChatGPT가 셸·빌드·테스트·Git까지 한 세션에서 직접
수행해야 하고 해당 OS 권한을 수용한다면 업스트림의 기능적 이점이 큽니다.**

둘은 단순한 최신판·구판이 아니라 다른 권한 모델입니다. 포크를 유지하면서
업스트림의 간결한 정상 경로와 중복 조정 감소 아이디어를 선별 적용하는 편을 권합니다.
터미널 전환·자동 채팅 삭제까지 포함한 전체 병합은 기존 파일 권한의 의미를 바꿉니다.
이는 포크의 [통합 정책](fork-policy.md)과도 맞지 않습니다.

## 4. 포크의 장점

### 4.1 권한을 구현으로 제한한다

`read`는 수정 요청을 단순히 금지하는 프롬프트가 아니라 파일 API가 적용하는 권한입니다.
`edit`도 선택한 프로젝트 안의 텍스트 변경에 한정됩니다. Git 메타데이터, 경로 탈출,
링크, Windows의 대소문자·짧은 이름·대체 스트림 등 우회 경로와 운영 설정·실행본·
비공개 런타임의 중첩을 검사합니다. 검토·문서화·제한된 코드 변경에서 권한 범위를
설명하고 사후 확인하기가 더 명확합니다. [도구 계약][F-workspace], [포크 정책][F-policy].

다만 `.env` 등 일반 프로젝트 파일은 비밀 필터의 대상이 아닙니다. 읽기 전용도 정보
노출을 막지는 않습니다. 소유한 OS 프로세스가 적대적으로 파일시스템을 바꾸는 환경의
격리나 모든 경쟁 조건에 대한 보장으로 확대 해석해서는 안 됩니다.

### 4.2 협업 충돌과 중단의 증거를 남긴다

파일 읽기에서 받은 전체 SHA를 쓰기·삭제의 전제 조건으로 사용하므로 이전 리비전의
수정은 거부됩니다. 원본·영수증·저널과 저장 결과 해시를 통해 변경 및 수집 과정을
대조할 수 있습니다. 불확실한 결과 후보나 저널을 무조건 재실행·초기화하지 않는
정책은 중단 후 중복 변경을 줄이려는 설계입니다. [도구 계약][F-workspace],
[결과 복구][F-recovery], [런타임 잠금·상태 구현][F-runtime].

이것은 모든 파일 변경을 하나의 트랜잭션으로 되돌리는 기능이 아닙니다.
해시가 맞아도 코드 의미나 테스트 결과가 올바르다는 보장은 없으므로 부모 검토는 남습니다.

### 4.3 운영 상태를 구분해 진단한다

`/health`는 생존 확인, 인증된 `ready`는 로컬 준비 상태, `tasks`는 진행·미수집 목록,
`reconcile`은 보존된 증거의 대조입니다. 중단된 수집은 `collect --resume`로 처리하되
무작정 브라우저 메시지를 다시 보내지 않습니다. 전송 기록과 UI 조작을 분리하고
같은 작업에 대한 중복 전송을 방지하는 상태도 둡니다. [클라이언트][F-client],
[전송 절차][F-dispatch], [초기 설정][F-setup].

선택적 Windows 운영 헬퍼와 유한 재시도 supervisor는 소유한 워커의 운영을 돕지만
부모 Codex나 브라우저의 자동 재개까지 제공하지 않습니다. 계정·ACL·터널·서비스 등록은
별도 배포 문제입니다. [운영 지침][F-operations].

### 4.4 기본 채팅 보존과 의존성 축소

채팅을 보존하면 실패 원인, 실제 도구 호출, 후속 검토 근거를 다시 확인할 수 있습니다.
삭제와 탭 닫기, 토큰 종료를 구분하는 것도 추적성에 유리합니다. 반대로 채팅과 로컬
복구 데이터가 남는 만큼 사용자가 별도의 보존 기간·민감정보 관리 정책을 정해야 합니다.
[포크 스킬][F-skill].

네이티브 PTY 의존성이 없어 터미널 실행 파일·빌드 도구 설치를 줄일 수 있습니다.
이는 브라우저·HTTPS·MCP 설정까지 간단하다는 뜻은 아닙니다. [설정][F-setup].

## 5. 포크의 단점과 비용

**첫째, 구현과 검증의 반복이 부모를 거칩니다.** 웹 워커가 코드와 테스트를 수정해도
로컬 테스트는 부모가 실행합니다. 실패를 전달하고 같은 채팅에서 새 작업 권한으로
보완하는 과정이 필요할 수 있습니다. 셸 한 번으로 끝날 검색·빌드·파일 변환도 파일 API만으로는
대체되지 않습니다. [포크 스킬][F-skill], [권한 정책][F-policy].

**둘째, 텍스트 API의 제약이 있습니다.** UTF-8·파일당 1 MiB 제한, 전체 파일 교체,
페이지별 읽기와 전체 SHA 유지, 링크 거부 때문에 대형·바이너리·특수 파일 작업에는
맞지 않습니다. 부분 읽기가 반환 맥락을 줄이더라도 전체 해시·상태 검증 비용까지
사라지는 것은 아닙니다. [도구 계약][F-workspace].

**셋째, 운영·문서 복잡도가 큽니다.** 여러 복구 상태, 호환성 규칙, 서비스 생명주기,
전송 증거 규칙을 유지해야 합니다. 보호 기능을 계속 추가하면서 정상 작업에도 모든
진단·검사를 반복하면 조정 비용이 커집니다. 이번 README 정비는 정상 경로를 앞에 두고
상세 복구 지침은 해당 문서로 연결하는 방식으로 이 부담을 줄입니다.
이는 문서·설계에 대한 평가이며 측정된 시간 단축 주장은 아닙니다.

**넷째, 제한된 파일 권한만으로 이후 실행이 안전해지지는 않습니다.** 워커가 수정한
테스트·빌드 스크립트·패키지 설치 훅을 부모가 실행하면 부모 권한에서 부작용이 생길 수
있습니다. 실행 전 변경을 검토하고 불신 코드는 적절히 격리해야 합니다. [포크 정책][F-policy].

## 6. 업스트림의 장점

**완결된 개발 작업의 자율성이 더 큽니다.** `exec_command`와 `write_stdin`을 통해
읽기·수정·테스트·빌드·Git·대화형 명령을 동일 위임 세션에서 수행할 수 있습니다.
작업에 필요한 도구와 OS 권한이 준비되어 있다면 부모에게 실행을 되돌리는 횟수를
줄일 수 있다는 구조적 이점이 있습니다. 실제 시간·사용량 절감 정도는 미측정입니다.
[업스트림 도구 계약][U-workspace].

**정상 작업 경로가 간결합니다.** 등록 응답의 connection 이름·registration ID를 재사용하고,
`dispatch`로 모드·전송·시작을 확인하며, `finish`가 작업별 대기·결과 반환·수집을 합칩니다.
검증된 결과를 불필요하게 다시 읽거나 보고된 검사를 무조건 중복 실행하지 말라는
지침도 조정 비용을 줄이려는 설계입니다. 다만 근거가 부족하거나 충돌·통합 변경이
있으면 검증이 필요하다는 예외는 남습니다. [업스트림 스킬][U-skill].

**사용 경로가 더 넓습니다.** Medium·High 경로와 사용자가 직접 제어하는
`webgpt open` 터미널 채팅을 별도로 제공합니다. 파일 포크가 의도적으로 제외한
기능이므로 단순한 누락이나 버그로 취급해서는 안 됩니다. [업스트림 스킬][U-skill].

## 7. 업스트림의 단점과 보안상 의미

**cwd는 권한 경계가 아닙니다.** 업스트림은 워커 OS 사용자의 전체 권한으로 터미널을
제공한다고 명시합니다. 읽기 전용 프롬프트나 작업 토큰은 악의적인 서로 다른 작업을
격리하지 않습니다. 이는 문서화된 권한 설계이며 인증 우회 취약점이나 자동 관리자
권한 상승을 발견했다는 뜻은 아닙니다. 허용한 OS 사용자에게 다른 프로젝트·키·운영
파일 접근이 있다면 그 권한도 위험 평가에 포함해야 합니다. [업스트림 계약][U-workspace].

계약상 자동 undo·리비전 검사·명령 allowlist·출력 절단·명령 timeout이 없습니다.
장시간·대량 출력 작업의 자원 사용과 동시 수정은 별도 운영 통제가 필요합니다.
작업 완료·취소·워커 종료 시 소유 세션을 종료하는 생명주기는 유용하지만,
그 자체가 프로젝트 격리나 재시작 후 세션 복원을 제공하지는 않습니다.
[업스트림 계약][U-workspace].

기본 채팅 삭제는 정리와 보존 데이터 감소에 장점이 있지만 나중에 실제 도구 호출과
실패 원인을 다시 확인하기 어렵게 만들 수 있습니다. 업스트림은 명시적 보존과
`open` 채팅 예외를 인정하므로 “항상 채팅을 삭제한다”라고 표현하면 부정확합니다.
[업스트림 스킬][U-skill].

`node-pty`와 설치 헬퍼는 추가 배포 표면입니다. 네이티브 구성의 설치·OS별 동작은
환경에서 검증해야 하며, 의존성이 있다는 사실만으로 현재 설치 실패나 보안 결함이
있다고 단정할 수 없습니다. [package.json][U-package], [업스트림 CI][U-ci].

## 8. 검증 체계의 차이

두 버전 모두 Windows·macOS·Linux × Node 22·24·26의 9개 CI 조합을 정의하고 있습니다.
포크는 Actions를 커밋 SHA로 고정하고 저장소 검사 후 독립된 스킬 설치본 검사를
수행하며 테스트 파일 동시성을 제한합니다. 업스트림은 태그형 Actions와
`npm ci --prefix skills/webgpt` 후 스킬 테스트를 실행합니다.
[포크 CI][F-ci], [포크 실행기][F-tests], [업스트림 CI][U-ci].

워크플로 정의가 있다는 사실은 특정 최종 커밋에서 모든 검사가 통과했다는 뜻이
아닙니다. 테스트 수가 많다는 사실도 실사용 성공률의 우열을 입증하지 않습니다.
이 문서는 브라우저 로그인·전송·실제 파일 변경·저장 결과·권한 종료를 포함하는
동일 조건 종단 간 비교를 수행하지 않았습니다. PR의 실제 CI 결과와 미실행 항목은
해당 PR의 최종 커밋 검증 기록으로 별도 확인해야 합니다.

## 9. 이번 정비와 후속 우선순위

후속 개선의 우선순위는 다음과 같습니다.

1. **실제 위임의 수용 증거 확보:** 설치·연결·전송·기여·부모 수용을 분리한 기존
   [검증 절차](verification.md)로 관측합니다.
2. **정상 경로의 조정 비용 줄이기:** 업스트림 connection 식별 재사용과 결합된
   완료 UX를 검토하되, 상태 권한·무결성·독립된 부모 수용을 유지합니다.
   실제 병목을 측정한 후 최소 범위로 구현합니다.
3. **터미널이 정말 필요할 때만 별도 실행 모드 검토:** OS 강제 격리, 제한된 마운트,
   최소 환경, 자격 증명·네트워크 통제, 자원 한도, 프로세스 종료 검증을 먼저 설계합니다.
   단순 opt-in·cwd·명령 금지 목록은 격리의 대체가 아닙니다. [포크 정책][F-policy].

## 10. 재현 범위와 출처

기준은 위 두 SHA의 스킬·도구 계약·설치·복구 문서, 클라이언트/런타임 관련 구현,
CI 정의와 의존성입니다. 과거 문서에 기록된 실험은 이번 검토의 실행 결과로
재사용하지 않았습니다. 전체 코드의 무결함 증명이나 외부 독립 보안 감사도 아닙니다.
토큰·시간·비용·실사용 안정성의 정량 우열은 현재 근거로 확정하지 않습니다.
