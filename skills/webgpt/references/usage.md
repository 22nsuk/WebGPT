# WebGPT 실사용 가이드

WebGPT는 로그인된 웹 ChatGPT가 연결된 프로젝트 파일을 직접 읽고 수정하도록 Codex가
작업을 맡기는 방식입니다. 사용자는 목표와 프로젝트를 지정하고, Codex는 연결·권한·전송을
확인한 뒤 결과를 수집하고 로컬 검증을 수행합니다. 설치나 연결이 필요하면
[setup.md](setup.md), 실제 등록·결과 수집 절차는 [workspace.md](workspace.md)를 따릅니다.

프로젝트를 연결한다는 설명은 [참고 프로젝트](https://github.com/faithforone/WebGPT)의
사용 방식과 같습니다. 다만 이 포크는 프로젝트 범위의 텍스트 파일 도구를 유지합니다.
참고 커밋 `b8206c57866cf574fdb65aa2aadc146a4ad2e469`의 터미널 실행 권한이나
`webgpt open` 명령을 가져오지 않습니다. 테스트·빌드·Git은 Codex가 로컬에서 담당합니다.

## 작업을 맡기는 예시

아래 경로와 목표를 실제 작업에 맞게 바꿉니다. `xh`/`xhigh`는 Extra High(기본값),
`p`/`pro`는 Pro를 요청합니다. 요청한 모드는 웹 UI에서 확인하며 임의로 바꾸지 않습니다.

**저장소 리뷰 — 프로젝트 전체 읽기 권한**

```text
WebGPT xh로 C:\projects\my-app 저장소의 로그인 흐름을 리뷰해줘.
프로젝트 루트 전체에 read 권한을 부여해서 관련 구현과 테스트를 직접 읽게 해줘.
재현 가능한 결함을 우선하고 파일 위치, 영향, 수정 방향과 검증하지 못한 점을 알려줘.
파일 수정은 하지 말고 Codex가 결과의 근거를 로컬에서 확인해줘.
```

**기능 구현 — 프로젝트 전체 수정 권한**

```text
WebGPT pro로 C:\projects\my-app에 검색 결과 필터를 구현해줘.
프로젝트 루트 전체에 edit 권한을 부여하고 기존 구조와 동작을 확인한 뒤 직접 수정하게 해줘.
기존 사용자 변경을 보존하고 관련 테스트도 필요한 범위에서 수정해줘.
WebGPT는 변경 파일과 실행하지 못한 검증을 보고하고, Codex가 diff를 검토하고
프로젝트의 테스트와 빌드를 로컬에서 실행해서 결과를 확인해줘.
```

실제 코드 작업에는 선택한 채팅에서 정확한 프로젝트의 파일 도구를 사용할 수 있는지
확인합니다. 관련 파일을 찾을 수 있도록 루트 전체를 `read` 또는 `edit`로 부여하고,
파일별 허용 목록으로 대체하지 않습니다. 직접 접근이 없으면 연결 문제를 보고합니다.
사용자가 패치만 요청하지 않았다면 텍스트 답변이나 패치를 Codex가 대신 적용하는 것으로
직접 구현을 대체하지 않습니다. 프로젝트 내부의 불필요한 비밀정보는 전달하지 않으며,
분리가 필요하면 정리된 프로젝트 사본을 사용합니다. 비공개 런타임 자료는 프로젝트 밖에 둡니다.

**조사 — 프로젝트 권한 없음**

```text
WebGPT xh로 이 주제의 공개 자료를 조사해줘: [주제와 핵심 질문].
기준 날짜, 출처 링크, 확인된 사실과 추정, 자료 간 불일치를 구분해줘.
로컬 프로젝트 접근은 필요 없어. Codex가 핵심 출처와 결론을 확인해줘.
```

조사는 `workspace` 없이 등록하거나 연결 없는 텍스트 작업으로 진행할 수 있습니다.
이 선택은 로컬 코드 작업의 접근 권한을 생략하는 우회 방법이 아닙니다.

## 후속 수정과 병렬 작업

관련 후속 작업은 보존된 같은 채팅에서 이어갑니다. 예를 들어 “방금 결과의 오류 처리도
검토해줘” 또는 “Codex 테스트에서 확인한 아래 실패를 같은 채팅에서 수정해줘”라고 요청합니다.
이전 등록이 실행 중이라면 먼저 현재 상태와 산출물을 확인합니다. `submit_result`로 이미
종료된 작업은 파일 접근이 닫히므로, 추가 읽기·수정에는 같은 채팅에 새 작업 ID와 새 토큰을
등록합니다. 종료된 ID나 회수된 토큰을 재사용하지 않습니다. 채팅 재사용은 전송 기록을
초기화하거나 불확실한 프롬프트를 다시 보내는 근거가 아닙니다.

독립된 일이면 다음처럼 분리할 수 있습니다.

```text
WebGPT로 두 작업을 병렬 진행해줘. 같은 프로젝트에 필요한 권한을 부여하되
A는 docs/의 사용자 문서, B는 tests/의 회귀 테스트를 담당하게 해줘.
각자 다른 작업자의 변경을 보존하고 공통 파일 수정이 필요하면 먼저 Codex에 알려줘.
Codex가 결과를 모아 일관성과 테스트를 확인해줘.
```

작업별 채팅·등록·비공개 전송 기록을 유지하고 수정 소유권을 겹치지 않게 나눕니다.
한 작업이 다른 작업의 변경에 의존하면 순서대로 진행합니다. 동시 실행 제한이나 throttling이
관찰되면 동시성을 줄이고, 동일 작업을 새 채팅으로 반복 생성하지 않습니다.

## 로컬 controller 연결 오류

controller 요청은 설정된 `127.0.0.1` 포트의 지정된 작업 경로에 직접 전송합니다.
HTTP 301·302·303·307·308 리다이렉트는 같은 주소의 다른 경로라도 따르지 않습니다.
다른 포트로 비공개 입력을 다시 보내거나, `checked`·`ack`를 다른 작업으로 바꾸지 않도록
`fetch`의 `redirect: 'error'`를 사용합니다. 리다이렉트 거부는 자동 대기 재시도 대상이 아니며,
CLI는 실패로 종료합니다. 일반 출력의 `fetch failed`만으로 리다이렉트를 확정하지는 않습니다.
브라우저 탐색이나 공개 MCP 터널의 동작을 바꾸는 설정은 아닙니다.

정상 Worker의 controller는 리다이렉트를 반환하지 않습니다. 이 오류가 발생하면 해당 포트의
프로세스와 로컬 중계 설정을 먼저 확인하고, 오류를 없애기 위해 리다이렉트 허용을 켜거나
Location 주소를 새 목적지로 사용하지 않습니다. 최초 요청은 이미 지정된 포트에 도착했으므로
실패만으로 작업이 실행되지 않았다고 단정할 수 없습니다. 특히 `ack` 처리 후 응답이 잘못됐다면
정상 controller 연결을 확인한 뒤 기존 `reconcile`과 `collect --resume`으로 저장 상태를
확인합니다. 작업 재등록·본문 재전송·결과 삭제·ack 재실행을 자동으로 수행하지 않습니다.

## 결과 확인과 보존

Codex는 일반 Node CLI로 등록, 전송 기록·잠금, 대기, 해시 검증과 수집을 처리합니다.
CUA는 문서화된 브라우저 조작에만 사용합니다. 클릭 반환만으로 전환 완료를 판단하지 않고
URL·메뉴·선택 상태를 확인하며, 전송은 실제 새 사용자 메시지로 확인합니다.
[dispatch.md](dispatch.md)의 증거 계약을 따르고 고정 대기나 무조건 재클릭하지 않습니다.

큰 파일 검토에는 `read_file`의 선택 인자 `offset`, `limit`, `maxChars`로 필요한 줄만
읽을 수 있습니다. 전체 파일의 SHA와 부분 범위가 함께 반환되며, 다음 범위를 읽을 때
SHA가 바뀌었다면 현재 파일 기준으로 다시 확인합니다. 파일을 수정할 때는 전체 내용을
읽은 뒤 교체합니다. 부분 발췌를 새 전체 파일로 저장하지 않습니다.

도구 패널은 이전 호출을 누적해서 보여줄 수 있습니다. 완료된 호출 목록을 한 번 확인하고
도구 이름·호출 식별자·대상으로 정확한 결과를 선택합니다. 보고서가 인용한 오류 문구만으로
실패를 판정하거나 같은 호출을 여러 번 집계하지 않습니다. 결과 파일과 검증 진행을 보존해
중단 후 이어서 확인하고, 수집 시 저장된 바이트의 무결성과 내용의 정확성을 구분합니다.

중단된 작업을 이어갈 때는 기존 작업 ID와 비공개 기록을 사용합니다. `ready`와
해시 검증을 포함하는 `reconcile`을 확인한 후 `collect --resume <작업-ID>`로 수집 단계를
이어갈 수 있습니다. 이미 수집된 결과는 다시 검증하고, 폐기된 결과는 폐기 상태를 유지합니다.
복구 경고나 파일 변조가 있으면 원인을 확인하며, 재전송하거나 새 작업으로 초기화하지 않습니다.

일반 `collect <작업-ID>`도 이제 ack 뒤에 기존 `reconcile`을 한 번 조회하여 같은 작업의
상태·결과 경로·SHA와 실제 결과 바이트를 다시 확인합니다. HTTP 성공 응답만으로
`collected: true`를 만들지 않습니다. 정상 반환 형식은 그대로이며, 이미 수집된 결과를
일반 collect로 다시 수집하려 하면 기존처럼 거부합니다. 재개 조회에는 `--resume`을 씁니다.

다른 부모가 그 사이 결과를 폐기하면 일반 collect는 `COLLECTION_DISCARDED`로 실패하며,
`collect --resume`은 `disposition: discarded`를 보여 줍니다. 사후 조회가 실패하거나 결과가
바뀌거나 수집이 확인되지 않으면 `COLLECTION_UNCONFIRMED`를 반환합니다. ack 응답의 전송
오류는 읽기 조회 한 번으로만 확인하고, ack 자체는 자동으로 다시 보내지 않습니다.
명시적 호출 중단, 리다이렉트 거부, 알려진 HTTP·저장 오류의 기존 처리도 유지합니다.
일반 수집과 `--resume` 모두 명시적인 `503 SHUTTING_DOWN` ack 거부는 원래 오류와
재시도 가능 표시를 그대로 전달하며, 이 경우 사후 조회나 ack 재전송을 자동으로 하지 않습니다.
ack 이후 조회 중 호출자가 중단해도 원래 중단 오류를 그대로 전달합니다. 이미 반영된 ack는
되돌리지 않으므로, 필요하면 나중에 명시적으로 `collect --resume`으로 상태를 확인합니다.
일반 collect의 이 두 오류는 CLI에서 안전한 필드만 출력하며 성공 결과를 출력하지 않습니다.
`acknowledgment: accepted`는 ack 호출이 오류 없이 응답했다는 뜻이지 상태 저장의 증명은 아닙니다.

이 확인에는 일반 수집당 controller 조회 한 번과 기존 재조정·파일 검증 비용이 추가됩니다.
`reconcile`은 전체 작업 목록과 기존 건강검사를 사용하지만 일반 collect 출력에는 다른 작업을
추가하지 않습니다. 이것은 특정 시점의 사후 확인이며 원자적 트랜잭션이나 롤백은 아닙니다.
오류가 나더라도 ack와 토큰 회수가 이미 반영됐을 수 있습니다. 이미 처리된 작업을 되돌리거나
재전송하지 말고, 정상 controller에서 기존 상태를 확인합니다. 수집 소유자는 한 부모로 유지합니다.

수집의 각 확인 단계에서는 선택한 작업의 결과 바이트만 한 번 검증합니다. 보존된 다른 작업의
결과까지 반복해서 읽지는 않습니다. 일반 수집과 미수집 결과의 재개 수집은 ack 전후 각각
한 번, 이미 수집·폐기된 결과의 재개 조회는 한 번 읽습니다. 검증 결과를 캐시하지 않으므로
나중에 결과가 바뀌면 새 조회에서 다시 거부합니다. 전체 결과 점검에는 기존 `reconcile`을
사용하며, 이 명령의 작업별 무결성·복구 경고는 그대로 유지됩니다. HTTP 조회 횟수와 전체
메타데이터 응답, Worker의 건강·복구 검사는 줄이지 않으므로 전체 작업이 상수 시간이 되거나
모델 토큰·네트워크 사용량이 줄었다는 뜻은 아닙니다.

WebGPT가 실행할 수 없는 테스트는 `NOT_RUN`으로 남깁니다. Codex가 변경 내용을 먼저
검토하고 권한 범위에서 실제 테스트·빌드를 실행하여 `PASS`/`FAIL`을 기록합니다. 실패 시
필요한 근거를 같은 채팅에 전달해 좁게 수정합니다. Git 검토·커밋·PR·push는 사용자 요청
범위에서 Codex가 담당하며 파일 수정 권한만으로 배포나 Git 작업 권한이 추가되지는 않습니다.

결과를 수집하고 토큰을 회수해도 작업 채팅은 기본적으로 보존합니다. 완료된 작업의 소유 탭만
닫고 비공개 기록에 채팅 URL을 남깁니다. 삭제는 사용자가 해당 채팅 삭제를 명시적으로
요청한 경우에만 수행하며, 보존 때문에 완료 통지나 토큰 정리가 계속 활성 상태로 남지 않습니다.
