# WebGPT와 직접 Browser/Chrome 사용: 선택 기준과 개선 우선순위

검토 기준: 2026-09-27, `22nsuk/WebGPT` main `5dee2f3ae7dbe48afafc020149e617b0380fcfa4`
(PR #47 병합 직후). 아래 기존 기능과 이번 첨부 확인 개선을 구분한다. 제품 지원 범위는
바뀔 수 있으므로 실제 설치 버전과 공식 문서를 다시 확인한다.

## 결론: 브라우저 엔진의 대체재가 아니라 위임 작업의 관리 계층

Browser/Chrome 도구는 페이지를 열고, 읽고, 클릭하고, 입력하는 실행 수단이다. WebGPT는
그 수단을 이용해 로그인된 웹 ChatGPT에 작업을 맡긴 뒤, 프로젝트 접근 권한·전송 기록·결과
수집·중단 후 대조·부모의 검증을 연결한다. 따라서 비교의 핵심은 클릭 성능이 아니라
**동일한 브라우저 조작 위에 어떤 작업 계약과 증거가 추가되는가**이다.

여기서 직접 사용은 현재 워크플로의 Browser/Chrome 조작을 중심으로 한다. OpenAI의
[내장 Browser](https://learn.chatgpt.com/docs/browser)와
[Chrome 확장](https://learn.chatgpt.com/docs/chrome-extension)은 같은 환경이 아니다.
내장 Browser는 별도 브라우저 프로필을 사용하고, 확장은 연결한 일반 브라우저의 탭과
로그인 환경에서 작업한다. 공식 문서는 현재 내장 Browser의 자동 파일 업로드를 지원하지
않는다고 설명하며, Chrome 파일 URL 권한 설정은 확장 경로의 설정이다.

별도 제품인 [Browser Use](https://github.com/browser-use/browser-use)를 가리키는 경우도
구분해야 한다. 이는 단순 클릭 함수만 있는 도구가 아니라 로컬 라이브러리, 기존 에이전트용
CLI, 사용자 정의 도구·구조화된 출력, 호스팅된 에이전트 등을 제공한다.
[Cloud API](https://docs.browser-use.com/cloud/quickstart)에도 작업 실행과 완료 대기가 있다.
따라서 “다른 도구에는 상태나 확장성이 전혀 없다”는 비교는 틀리다. WebGPT의 차별점은
웹 ChatGPT와 이 프로젝트의 로컬 파일/결과 계약에 맞춘 통합이며, 해당 기능들을 다른
프레임워크로 구현하는 것 자체가 불가능하다는 뜻은 아니다.

```text
Codex 부모: 범위·권한·소유권 결정, 로컬 검증, 승인된 Git/PR 작업
    │
    ├─ 허용된 Browser/Chrome → 웹 ChatGPT에 작업 위임
    │                            │
    │                            └─ 작업 토큰 → 프로젝트 텍스트/MCP 결과 도구
    │
    └─ 로컬 controller → 등록·대기·수집·재개 대조
         private ledger → 대상 채팅·전송 시도·관찰 증거 보존
```

구조의 근거는 [SKILL](../SKILL.md), [workspace](workspace.md),
[dispatch](dispatch.md), [client](../scripts/client.mjs)다. WebGPT는 자체 브라우저
업로더나 범용 셸 실행기를 추가하지 않는다.

## 실제 차이가 나는 부분

| 비교 항목 | Browser/Chrome 직접 사용 | WebGPT가 더하는 것과 한계 |
| --- | --- | --- |
| 작업 단위 | 페이지/탭에서 요청한 조작을 수행 | 목표·소유권·입출력·채팅·완료/정리 상태를 같은 작업으로 연결 |
| 모델 사용 | 직접 웹 ChatGPT를 열고 같은 모드를 선택할 수도 있음 | 요청한 Pro/Extra High의 실제 UI 선택 확인을 작업 규칙에 포함. 모델 접근 자체가 독점 기능은 아님 |
| 프로젝트 맥락 | 부모가 이미 가진 파일 도구를 쓰거나 필요한 내용을 전달할 수 있음 | 위임받은 웹 ChatGPT가 등록 프로젝트를 직접 탐색/읽기. 부모가 매번 파일을 중계할 필요를 줄일 수 있음 |
| 프로젝트 변경 | 부모의 로컬 도구나 별도 연결을 사용 | 프로젝트 루트와 read/edit 권한, 읽은 revision을 전제로 한 수정 충돌 거부, 복구 증거 보존 |
| 전송 불확실성 | 직접 조작에서도 자체 확인 로직을 만들 수 있음 | 대상·본문·이전/새 메시지 증거, 잠금과 durable sending 상태. 응답 유실을 곧바로 재전송하지 않음 |
| 결과 수집 | 화면 결과를 읽거나 별도 저장/콜백을 구성 | submit_result 저장, 작업별 대기, 저장 바이트 무결성 검사와 조건부 수집, 토큰 종료 |
| 중단/재개 | 브라우저 상태와 이전 실행을 다시 파악 | 보존된 작업 기록·채팅·controller 상태·결과를 대조. 브라우저와 부모가 자동 재개되는 기능은 아님 |
| 병행 작업 | 탭/에이전트를 병렬로 사용할 수 있음 | 작업 ID·소유권·scoped wait로 다른 작업과 구분. 충돌 없는 병렬 설계는 여전히 부모 책임 |
| 검증 | 직접 사용도 결과를 검증할 수 있음 | 전송 관찰, 파일 무결성, 로컬 테스트, 내용 검토를 구분하는 기존 절차. 모델의 PASS 주장은 실행 증거가 아님 |
| 운영 부담 | 단순 작업에서는 적은 준비로 끝날 수 있음 | worker/controller, 연결, private runtime/ledger, 설치본 일치 등을 관리해야 함 |

### 1. 가장 큰 실익은 파일을 반복 전달하지 않는 협업

여러 소스 파일을 읽어야 하는 검토나 수정에서는 “파일을 골라 붙여 넣고 답을 다시 옮기는”
부모의 반복 중계가 부담이 된다. WebGPT의 위임 대상은 등록된 프로젝트에서 필요한 파일을
직접 읽고, edit 작업이면 실제 수정할 수 있다. [workspace](workspace.md)의 디렉터리/입력
페이지와 revision 계약은 큰 프로젝트에서도 전체가 보인 척하거나 오래된 바이트를 기준으로
덮어쓰는 것을 피하도록 돕는다.

다만 부모 Codex도 원래 파일을 편집할 수 있으므로 **파일 편집 자체**가 차별점은 아니다.
웹 ChatGPT 쪽 협업자에게 범위가 있는 접근을 주고, 부모가 로컬 테스트와 통합을 맡는
역할 분담이 핵심이다. 파일 권한은 프로젝트 루트와 read/edit 모드 기준이지, 임의의
파일별 허용 목록이나 범용 운영체제 샌드박스라는 뜻이 아니다.

### 2. “화면상 끝남”과 “검증된 결과 수집”을 분리

[client](../scripts/client.mjs)의 대기·수집·재개 대조는 브라우저의 답변만 보고 끝내는 대신
작업 결과와 저장된 바이트, 수집 상태를 확인하게 한다. 작업이 끝났다는 모델의 설명,
본문이 전송되었다는 UI 증거, 저장된 파일의 해시 일치, 테스트 실제 통과는 서로 다른 사실이다.
이 구분은 긴 작업과 세션 인계에서 특히 유용하다.

추가 검증은 비용도 든다. 짧은 질문 한 번에 worker 등록과 결과 수집을 항상 붙이면 오히려
느려질 수 있다. 일반 텍스트 작업에는 필요 없는 프로젝트 connector를 요구하지 않는다.

### 3. 불확실성을 지우기보다 보존

[dispatch](dispatch.md)의 동일 ledger 잠금과 `sending`/`uncertain`은 “클릭 응답을 못 받았으니
다시 보낸다”는 중복 작업을 막는 데 유용하다. 하지만 exactly-once 브라우저 전달, 강제 종료
후 자동 복구, 별도 ledger 복사본의 동기화까지 보장하지 않는다. 안전하게 멈추면 부모가
보존된 채팅을 확인해야 하므로, 개입 횟수도 실사용 지표에 포함해야 한다.

[운영 가이드](operations-windows.md)의 worker 재시작도 브라우저 재시작·로그인 복구·부모
에이전트 재개와는 다르다. 설치본과 운영 환경을 별도로 확인해야 한다.

### 4. 보안과 비용에 대한 과장 금지

작업 토큰과 프로젝트 범위, read/edit 분리, 경로/충돌 검사, 결과 수집 후 토큰 종료는
권한과 상태를 더 명시적으로 만든다. 반대로 로컬 runtime과 연결을 운영하는 비용과 위험도
추가된다. private 파일/계정·승인된 네트워크 경계를 신뢰하는 설계이며, 토큰을 가진 행위자나
악의적인 로컬 관리자까지 격리하는 보장은 아니다. 브라우저 사이트 승인도 그대로 필요하다.

위임으로 부모의 파일 중계와 추론 부담이 줄 가능성은 있지만, 전송·기다림·검토 비용이
추가된다. 같은 Pro 모드에 직접 Chrome으로 접근하는 경우와 비교해 구독 사용량이나
토큰이 얼마나 절약되는지는 아직 측정하지 않았다. 더 빠름, 더 저렴함, 더 높은 코드 품질을
일반적인 사실로 제시하지 않는다.

## 언제 어느 쪽을 선택할까

| 작업 | 권장 출발점 | 이유 |
| --- | --- | --- |
| 페이지 하나 확인, 짧은 질문, 한 번의 폼 조작 | 직접 Browser/Chrome | 위임 관리의 추가 비용이 실익보다 클 수 있음 |
| 여러 파일을 읽는 독립 검토, 충분히 긴 설계/분석 | WebGPT 검토용 read 작업 | 직접 프로젝트 접근과 보존된 결과/증거가 유용 |
| 독립된 범위의 코드 수정 + 부모의 로컬 통합/테스트 | WebGPT edit 작업 | 역할 분담과 revision 충돌 검사가 맞음 |
| 일반 사이트의 대량 반복 수집/브라우저 서비스 구축 | 목적에 맞는 브라우저 프레임워크부터 검토 | WebGPT는 범용 브라우저 인프라 제품이 아님 |
| PDF/이미지 등 웹 ChatGPT 첨부가 필수 | 지원되는 실제 업로드 경로 확인 후 결정 | 프로젝트 텍스트 접근이나 read_input은 첨부 대체물이 아님 |

명시적으로 WebGPT 사용을 요청한 작업을 임의로 다른 모델/로컬 구현으로 바꾸라는 규칙은
아니다. 작업의 전달 방식·권한·필수 입력이 달라지는 변경은 기존 사용자 지시를 따른다.

## 이번에 구현한 개선: 필수 첨부 확인을 문서에서 실행 계약으로

PR #47은 먼저 `begin`, 이후 업로드/준비 확인, 본문 전송, 동일 메시지 첨부 확인, 마지막
`confirm`이라는 올바른 순서를 문서화했다. 그러나 기존 version-1 helper는 본문/대상만
검증했다. 부모가 확인 절차를 놓치면 첨부 없이도 `submissionConfirmed: true`가 될 수 있었다.
이는 실제 Chrome 업로드 장애 원인이 확인되었다는 뜻이 아니라, 그 실패를 완료로 오인할
수 있는 **부모 측 확정 절차의 빈틈**이다.

이번 변경은 [기존 dispatch helper](../scripts/dispatch.mjs)만 확장한다.

- 새 첨부 작업의 최초 등록에서 `requiredAttachments`를 선언한다. helper가 version 2로
  저장하며 재등록으로 제거하거나 바꿀 수 없다. 기존 version 1은 자동 이전하지 않는다.
- 동일한 새 사용자 메시지의 `userMessage.attachmentNames`가 선언한 이름/개수와 일치해야
  확정된다. 누락·중복·다른 이름·추가 파일은 불확실 상태로 남고 재전송은 계속 차단된다.
- 첨부 작업을 high-level `dispatchPrompt`로 보내려 하면 브라우저 콜백 전에 거부한다.
  기존 split begin/upload/send/confirm 흐름과 잠금을 재사용한다.
- 공개 요약에는 개수와 `attachmentEvidenceConfirmed`만 추가한다. 파일명·경로·채팅 ID·
  토큰을 출력하지 않는다. 텍스트 전용 기존 출력과 controller/MCP 계약은 유지한다.

정확한 입력과 업그레이드 경계는 [dispatch](dispatch.md#required-attachments-use-the-split-cli-and-a-deferred-confirmation),
실제 업로드 진단은 [file-uploads](file-uploads.md)를 따른다. UI에서 관찰한 이름을 대조하는
것이므로, 같은 이름의 다른 바이트·거짓 관찰·원격 파싱 실패까지 검증하지 않는다. 업로드
준비 확인 자체도 부모 책임이다. Chrome 확장·네트워크·권한을 고친 PR로 해석하면 안 된다.

## 후속 개선 우선순위와 측정 방법

| 우선순위 | 개선 방향 | 판단 기준 / 범위 |
| --- | --- | --- |
| 이번 구현 | 필수 입력 누락의 완료 오인 방지 | 불완전 증거에서 false, 재개 후 확인 대기 유지, 정상 작업/기존 텍스트 흐름 보존 |
| 다음 실환경 검증 | 실제 backend/profile/path와 업로드 실패 단계 확인 | 수동 업로드 대조군과 작은 비밀 없는 파일. 브라우저 미접속이면 NOT_RUN, 원인 단정 금지 |
| 반복 작업 개선 | 부모의 불필요한 상태 확인·파일 중계·긴 반복 지시 줄이기 | 기존 scoped wait/입력 창/같은 작업 인계를 먼저 사용. 새 dashboard나 큐부터 만들지 않음 |
| 효과 검증 | 직접 사용 대비 실익을 같은 기준으로 비교 | 같은 과제/입력/권한/완료 기준, actual mode, 시간·개입·성공률·출력 품질을 함께 기록 |
| 확장 여부 결정 | 실제로 반복되는 병목만 자동화 | 승인/업로드/화면 읽기 계약을 확인한 기능만 지원. 추측한 셀렉터·비공개 API·무조건 재시도 금지 |

비교 실험은 [기존 verification workflow](verification.md)를 재사용한다. 자동화 테스트에서
검증한 파일/상태 전이는 실환경 성능 벤치마크가 아니다. 실제 비교에서는 시작/종료 정의를
맞추고, 전체 경과 시간, 부모의 능동 개입 시간, 도구 호출/중복 확인 횟수, 재시도와 불확실
차단 건수, 실제 테스트 결과와 내용 검토의 수용/부분수용/거부를 함께 기록한다. 업로드 작업의
`sendingAt → submittedAt`에는 파일 준비와 확인 시간이 포함되므로 순수 전송 지연으로
비교하지 않는다. 표시되지 않는 토큰/요금은 추정값으로 채우지 않는다.

단 한 번의 성공 사례로 속도·비용·안정성 우위를 선언하지 않는다. 몇 차례 반복해도 직접
사용보다 준비/개입이 큰 작업은 직접 사용 경로를 선택하는 것이 합리적이다. 이 문서와
코드 변경은 그러한 선택을 돕는 것이며, 모든 작업을 WebGPT로 옮기자는 제안이 아니다.
